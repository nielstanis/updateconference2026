# Threat Model: eShop (.NET reference application)

## 1. System context

eShop is Microsoft's canonical .NET e-commerce reference application ("AdventureWorks" storefront), built on .NET 10 and .NET Aspire 13.6. It is a distributed application of 19 `src` projects: ASP.NET Core minimal-API services (Catalog, Ordering, Webhooks), a gRPC service (Basket), a self-hosted Duende IdentityServer 7.3.2 on ASP.NET Core Identity (Identity.API), two background workers (OrderProcessor, PaymentProcessor), Blazor Server front ends (WebApp storefront and WebhookClient), two .NET MAUI clients (ClientApp native, HybridApp Blazor Hybrid), a YARP-based mobile BFF, and shared libraries for service defaults (JWT bearer, OpenTelemetry, health checks), the RabbitMQ event bus and an EF Core transactional outbox. State is three containerized backing services orchestrated by the Aspire AppHost: one PostgreSQL instance (image `ankane/pgvector:latest`) hosting four logical databases (`catalogdb`, `identitydb`, `orderingdb`, `webhooksdb`), one Redis for baskets, and one RabbitMQ broker for integration events. Optional AI features (Azure Microsoft Foundry `gpt-4.1-mini` / `text-embedding-3-small`, or local Ollama) drive catalog semantic search and the storefront chatbot.

The app is deployed by running `aspire run` locally (Aspire dashboard) or `aspire deploy` into an Azure Container Apps environment; only `identity-api`, `webapp` and `mobile-bff` get external endpoints, while catalog, ordering, basket, webhooks and the workers are internal. The intended audience is developers learning a services-based .NET architecture, and the README explicitly states that the containerized PostgreSQL, Redis and RabbitMQ used in the Azure deployment are "intended for evaluation and demonstrations, not production data." The checkout is ~650 source/config files at commit `913acea`, with 467 commits since the 2023 rewrite; the older eShopOnContainers history is not present, so security discussion predating the rewrite is out of scope. There is no `SECURITY.md`, `CHANGELOG` or architecture document at HEAD.

## 2. Assets

| asset | description | sensitivity |
|---|---|---|
| JWT/OIDC signing private key | RSA-2048 private key (full D, P, Q, DP, DQ, QI) committed as `src/Identity.API/tempkey.jwk` and loaded by `AddDeveloperSigningCredential` with key management disabled; possession allows minting tokens for orders, basket and webhooks. | critical |
| User credentials and password hashes | ASP.NET Identity `AspNetUsers.PasswordHash` (PBKDF2) in `identitydb`, plus seeded demo users `alice`/`bob` with password `Pass123$` re-created on every startup. | critical |
| Identity PII and card fields in user profile | `ApplicationUser` persists card number, security number (CVV), expiry, cardholder name, full address, email and phone; `ProfileService` emits them as id-token/userinfo claims (`card_number`, `card_security_number`, `address_*`). | critical |
| OIDC client secrets and long-lived tokens | Hardcoded client secret `secret` for `webapp`/`maui`/`webhooksclient` (the MAUI app ships it as a default); offline access enabled with default refresh-token lifetimes. | high |
| Order PII and order history | `orderingdb` orders (address owned entity), buyers (`IdentityGuid`, name), order items and masked payment methods; exposed through Ordering API, WebApp and mobile BFF. | high |
| Payment data | PAN masked to `XXXX-last4` before storage; CVV not mapped in the Ordering model; PaymentProcessor is a simulated stub with no real gateway or tokenization. The Identity profile still stores and emits CVV. | medium |
| Basket contents (Redis) | Per-user `CustomerBasket` JSON at Redis key `/basket/{userId}` with no encryption at rest, on the shared unsegmented Redis instance. | medium |
| Catalog integrity | `catalogdb` Catalog/Brand/Type rows including price, stock thresholds and embeddings; create/update/delete endpoints are anonymous; price changes publish integration events. | high |
| Catalog product images | `Pics/*.webp` served from the local filesystem through the picture endpoint and the WebApp/BFF proxies. | low |
| Webhook subscriptions and signing tokens | `webhooksdb` Subscriptions (`DestUrl`, `Token`, `UserId`, `Type`); order payloads are POSTed to subscriber URLs with an `X-eshop-whtoken` header; tokens are logged in cleartext. | high |
| Inbound webhook validation token | `WebhookClientOptions:Token` GUID committed in `appsettings.json` and used (optionally) to accept `/check` and `/webhook-received`. | medium |
| Event bus messages (RabbitMQ) | Integration events carry buyer name/identity, order id and status, stock items and price changes; outbox copies live in each service DB; one broker serves all services without TLS or per-service vhosts. | high |
| Database connection strings and credentials | Dev `appsettings` contain a postgres superuser password (`yourWeak(!)Password`) explicitly whitelisted from CredScan; Aspire injects one shared superuser credential at runtime. | high |
| Service availability | One PostgreSQL container for four databases, one Redis and one RabbitMQ with no replicas or backups; an Identity outage breaks all authentication and a RabbitMQ outage halts the order saga. | high |
| Downstream LLM prompt and PII flow | Chatbot function tools serialize the signed-in user's name, address, email, phone and cart contents into prompts sent to Foundry/Ollama; catalog text is sent for embeddings. | high |
| Sensitive data in logs and OpenTelemetry | The MediatR logging behavior serializes the entire `CreateOrderCommand` (including CVV and masked PAN); webhook tokens are logged; OTLP export is enabled by environment variable. | high |

| RabbitMQ event bus consumers | All services consume integration events from one exchange; messages are JSON-deserialized and dispatched, ACKed even on handler exception (no dead-letter queue). ## 5. Deprioritized

| threat | reason |
|---|---|
| Deserialization gadget RCE via request bodies or broker messages | System.Text.Json with concrete DTOs only; no TypeNameHandling, BinaryFormatter, XmlSerializer or polymorphic converters found in src/. |
| SQL injection in catalog, ordering, webhooks or outbox queries | All data access is EF Core LINQ or parameterized Npgsql; no FromSqlRaw/ExecuteSqlRaw or interpolated SQL found. |
| CSRF against the backend APIs | Catalog/Ordering/Webhooks authenticate with bearer tokens rather than ambient cookies; Blazor and Identity MVC POSTs carry antiforgery tokens. |
| Clickjacking or reflected XSS on the Identity UI | SecurityHeadersAttribute sets CSP default-src 'self', frame-ancestors 'none', nosniff and no-referrer on Razor views. |
| Repudiation of catalog and order mutations | No tamper-evident audit log exists, but this is a reference sample; OpenTelemetry logs are operational, not accountability records. Revisit for real commerce. |
| Production health-probe mismatch causing restart loops | The Aspire-generated Container Apps manifest is not in the tree, so the Production mapping of /health cannot be verified. |
| Aspire dashboard token disclosed via the login URL | The dashboard is a local developer surface and is not part of the deployed topology. |
| Denial of service against PostgreSQL or RabbitMQ from the internet | Both are internal-only in the AppHost topology; a compromised service is covered by T3 and T20. |
| Compromise of the Dependabot update channel itself | Speculative second-order supply-chain risk; Dependabot is currently the primary patch control (T15). |
| Extraction of tokens from MAUI SecureStorage on a rooted or jailbroken device | Platform keystore control; requires the local privileged access already assumed by T19. |

## 6. Open questions

- Is this checkout ever deployed somewhere reachable from the internet, or is it only a local/demo environment? This decides whether T1 and T2 are "sample-only" or genuinely critical in context.
- Which container base image and tag does Aspire generate for each service, and is the .NET runtime inside already patched past 10.0.12? The repo pins class libraries at 10.0.12 but contains no Dockerfiles.
- Does the mobile BFF restrict HTTP methods on `/api/catalog/{*any}`, or can internet clients reach the anonymous Catalog write endpoints through it?
- Is Foundry or Ollama enabled in the deployed environment, and is there a data-processing agreement or PII-scrubbing requirement covering the chatbot prompt flow?
- Who is intended to hold an `orders` or `webhooks` token, and is any role separation (customer vs. operator) expected? Ordering currently has no role model.
- Is there an ingress or WAF in front of `identity-api` that rate-limits login and sanitizes `X-Forwarded-For` before it reaches the loopback diagnostics check?
- Are webhook subscribers trusted partners or self-service users? The grant-URL tester treats any reachable host as a valid destination.
- Was the committed `tempkey.jwk` reused in any environment where real accounts exist, or was a separate signing key provisioned out of band?
- What is the retention and access policy for the OpenTelemetry backend that receives logs containing card data and webhook tokens?
- Is `aspire destroy` permitted in a shared subscription, and is the resource-group layout reviewed before deployment?
- Are the seeded users `alice`/`bob` acceptable in the target environment, or should user seeding be disabled outside Development?
- What is the acceptable availability posture for this sample? There are no availability requirements, SLOs or backup retention documented in the tree.
