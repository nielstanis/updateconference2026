## Scenarios

The scenarios are grouped by causal mechanism, not by count. They are readings of source with prerequisites, not three confirmed defects. Each is tagged as a code-observed weakness (a code reading supports it) or a design hypothesis (a possible scenario with unmet or unobserved prerequisites). All are runtime-unverified: no deployed instance was observed. Repeated readings of one file are not independent corroboration.

### Family 1: downstream operation authority

1. **Catalog write routes without authentication.** `tm02:T-catalog-unauth-write` (medium). Code-observed weakness, runtime-unverified. Catalog.API maps create, update and delete item routes without an authorization requirement and registers no authentication; any caller that reaches the service could change prices, text, picture names or stock fields. Reach from the internet depends on the gateway passing write methods (G2), which is unobserved; reach from inside the environment needs only a foothold on any workload. Related hypotheses with low confidence: `tm02:T-catalog-price-and-event-tampering`, `tm02:T-catalog-text-poisoning-embedding`. Attack paths `tm02:AP-catalog-bff` and `tm02:AP-catalog-internal` are conditional. [Likely 🟡]
2. **Ordering operations without ownership or role checks.** `tm02:T-orders-read-any-order`, `tm02:T-orders-cancel-ship-any-order`, `tm02:T-orders-create-foreign-userid`, `tm02:T-orders-client-supplied-item-prices` (all medium). Code-observed weakness, runtime-unverified. Order routes require an authenticated caller, but the by-id read has no owner filter, cancel and ship do not compare the caller to the order owner or require a role, create accepts a user id from the body, and item prices come from the client. Whether a customer token reaches Ordering through the gateway depends on header forwarding that was not observed (G-s01-bff-auth-forwarding), and no ownership rule was supplied (GAP-invariants). [Likely 🟡]
3. **Shared token validation without audience or scope.** `tm02:T-jwt-audience-scopeless-cross-api` (medium). Code-observed weakness, runtime-unverified. Basket, Ordering and Webhooks share one configuration that validates issuer, signature and lifetime but not audience, and no operation-level scope or role policy was found; a token minted for one client could be accepted by another API. Which scopes the services are meant to enforce is unknown (G4, G5). [Likely 🟡]
### Family 2: context carried or replaced across hops

4. **Event identity and replay on the broker.** `tm02:T-bus-forged-order-lifecycle-events`, `tm02:T-bus-forged-paid-stock-and-notifications` (medium), `tm02:T-bus-forged-orderstarted-basket-delete` (low). Design hypothesis, runtime-unverified. Integration events travel on a shared broker with no sender identity or signature in the message, and consumers act on event fields without checking the order; a forged Paid event could remove stock for an order that does not exist. This needs broker access, whose credentials and network policy are unobserved (UB2, G3). Only registered event types are deserialized, which limits but does not remove the scenario. Attack paths `tm02:AP-order-bus` and `tm02:AP-bus-paid` are conditional. [Likely 🟡]
### Family 3: business effects under retry and partial failure

5. **Retry reports success for work that did not happen.** `tm02:T-orders-request-id-consumed-failure-reported-ok` and `tm03:T-orders-cancel-ship-retry-reports-success` (medium). Code-observed weakness, runtime-unverified. The request id is stored before the inner command, the handler swallows the inner failure and the transaction commits, so a retry with the same id gets a canned success. For create the first reply is also 200 OK; for cancel and ship the first reply is a 500 and the retry returns 200. Whether real clients reuse the id on retry was not read (UN-005). [Likely 🟡]
6. **Consumers acknowledge on failure.** `tm02:T-bus-ack-on-failure-message-loss` (medium). Code-observed weakness, runtime-unverified. The consumer acknowledges every message including after an exception, with no retry or dead-letter path, so a transient failure can leave an order in AwaitingValidation or StockConfirmed. The first step is re-published by the order processor and does recover; no equivalent re-driver was found for the later steps. A reconciler outside the files read may exist (G-s01-retry-recovery). [Likely 🟡]
7. **Cancel racing payment.** `tm03:T-cancel-races-payment-no-compensation` (low). Design hypothesis, runtime-unverified. A cancel during the payment step leaves a Cancelled order with a success payment outcome and no void or refund path in the code read. Payment is simulated in the shipped code, so no money moves; the scenario matters for a copy that adds a real gateway. [Likely 🟡]
### Other readings

Medium-confidence code-observed weaknesses outside the three families: seeded users with published credentials created at startup (`tm02:T-seeded-users-known-credentials`), and webhook grant tokens written to logs with a sample receiver that accepts an empty token (`tm02:T-webhook-token-logged-and-sample-receiver-open`). [Likely 🟡]
The remaining threats are low-confidence design hypotheses: chatbot tool abuse and claim disclosure, picture file name read, client registry secrets and a client without PKCE, implicit-flow Swagger clients, developer signing key, webhook SSRF and cross-user fan-out, card data in logs, forwarded-header trust, CI and image supply chain, shared database credential, operator control plane authority, and simulated payment marking orders paid. Full list in the JSON `threats` collection. [Likely 🟡]
